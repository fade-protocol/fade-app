# Fade

**A permissionless payout protocol for Solana.** Any app (a program over CPI, a
server or a wallet) can attach a fixed-odds payout to a payment, a reward or a
game, with odds anyone can verify on-chain, without holding a prize fund or
integrating a randomness oracle. Anyone can fund the shared vault by
providing liquidity.

> Status: pre-alpha, built for the Colosseum Crypto World's Fair. The program
> runs on Solana devnet, behind the app at https://app.fade.finance, the keeper
> at https://api.fade.finance and the landing at https://fade.finance.

## How it works

The integrator supplies a ticket price and a **payout table**: up to 32 `(probability,
multiplier)` pairs. Fade checks on-chain, in exact integer arithmetic, that the
payout table cannot pay out more than it takes in on average, reserves the worst-case payout
against a shared USDC vault, draws the outcome from an oracle VRF seeded with a
block hash that does not exist when the ticket opens, and settles. Product design,
interface and distribution stay with the integrator; solvency, fairness and
randomness belong to the protocol.

Liquidity providers deposit USDC into the vault, earn the vault margin on
every ticket, and carry the variance. Deposits and withdrawals clear at
one price per epoch, so a known result can never be front-run.

## Toolchain

Everything is pinned in `toolchain.env` and installed under
`~/.local/share/fade-tools` without touching any global Solana, Anchor or Rust
installation:

```sh
git clone https://github.com/fade-protocol/fade-app.git
cd fade-app
pnpm install
pnpm tools:install   # Agave, Rust, anchor-cli, platform-tools; several minutes the first time
pnpm tools:doctor
pnpm build:sbf       # builds every program as SBPF v3 and refreshes idls/
pnpm test:rust
pnpm test:ts
```

Programs are built as **SBPF v3**, which is active on mainnet and devnet
(feature `enable_sbpf_v3_deployment_and_execution`). Tests run on the mainnet
feature set, never on a harness default.

## The build fails on a stack frame overflow

A Solana function whose stack frame exceeds 4 KiB writes into the neighbouring frame: the
program still links, still loads, and then returns corrupted values at runtime. The linker
reports it as `Error:` and exits 0, so it does not fail a build on its own. `scripts/build-sbf.sh`
greps for it, fails, and deletes the binaries so no test can pick up a corrupted one.

The usual cause is an Anchor accounts struct deserialising large accounts onto the stack:
`Initialize` reached 4 160 bytes across its sixteen accounts. The fix is `Box<Account<'info, T>>`.

The toolchain was proven end to end before any product code was written:

| litesvm 1.4.1 (npm) + Codama client + TypeScript 7 + vitest 5 | same three checks through the generated client |
| Devnet | program `3FLR2XiNRr4WYT8qeac3zu2Xeo6qGvAirtdH9ZNhKC7T` deployed as v0, upgraded in place to v3, `ping` executed on both |
| ORAO VRF on devnet | `request_v2` paid by a program PDA (`vrf-payer`), recorded as `client`; fulfilled after **~10 slots (1.6 s)**; `RandomnessV2` layout as documented; 3 208 960 lamports returned to the PDA, net cost 1 646 200 lamports = 300 000 fee + 1 346 200 rent locked in the request account |
