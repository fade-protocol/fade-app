# Fade Spec 05 — Governance and Upgrade Safety

Domain: who holds power over the program and the LP vault, how that power is time-boxed, and what happens when something breaks. Every non-obvious factual claim below is sourced; where a source didn't say something, that gap is stated rather than filled from memory.

---

## 0. Executive summary

**The honest framing:** Fade is team-governed in V1. The upgrade authority is the dominant risk in the system — full stop, no amount of Fade-level parameter design changes that. What this spec does is (a) make that authority multisig-held, hardware-key-signed, and timelocked so a compromise is loud and slow instead of silent and instant, (b) make sure the timelock's delay is actually usable by LPs rather than theatrical, (c) draw a hard line around a small set of admin capabilities that must **never** exist because they'd be strictly worse than the upgrade key itself, and (d) give a dated, milestone-gated path to reducing this power instead of promising a burn date nobody can defend for unaudited code.

**Recommended configuration:**

| Authority | Holders | Threshold | Timelock | Can touch |
| --- | --- | --- | --- | --- |
| **Upgrade Council** | Squads v4 multisig, hardware-wallet signers only, geographically/organizationally distributed | 4-of-7 | 72h Squads-enforced, starts when threshold is reached | Program upgrade, upgrade-authority transfer, VRF/oracle program-id change, treasury address |
| **Parameter authority** | Same 4-of-7 Squads multisig (V1), separate PDA/config-authority slot from the upgrade authority | 4-of-7 | Per-parameter, enforced **inside Fade's own program logic** (not just Squads UI) — see §3 table | The LP floor and the protocol share, the cap's censorship term, the integrator ceiling, progressive credit once enabled, the breaker thresholds, `min_price`, `epoch_length_seconds`, `T_SETTLE`, `CLAIM_FEE`, `STRIKE_FEE`, `STRIKE_REWARD`, `FUND_TARGET`, the minimum request |
| **Pause Guardian** | 2-of-3 subset of Upgrade Council + one on-call engineer | 2-of-3 | None to pause (by design); un-pause requires the 4-of-7 council | Three independent pause flags + per-integrator targeted pause — never funds, never payouts |
| Upgrade authority itself | **Not burned in V1** | — | — | Rationale in §7 |

The single most load-bearing design choice below is procedural, not cryptographic: **queuing any upgrade must trigger `paused_new_tickets=true` as a separate, immediate step before the 72h clock starts**, so that reserved LP liability decays toward zero during the delay instead of sitting frozen and unexercisable for three days. That single rule is what makes §2's timelock a real LP protection rather than a compliance decoration.

## 1. Solana upgrade mechanics, and what a "small team" can actually do today

### 1.1 How upgrades actually work

Solana's default deployment path is the upgradeable BPF loader (loader-v3). It splits a program into an immutable **Program** address (what callers invoke) and a mutable **ProgramData** account (the actual bytecode) \[[Solana docs — Program Deployment](https://solana.com/docs/core/programs/program-deployment)\]. An `Upgrade` instruction, signed by whichever account currently holds the **upgrade authority**, replaces the bytecode at that ProgramData account atomically, in one instruction — there is no built-in delay of any kind \[[Solana docs — bpf\_loader\_upgradeable](https://docs.rs/safecoin-program/latest/solana_program/bpf_loader_upgradeable/index.html)\]. The upgrade authority can be reassigned via `SetAuthority`, and can be set to `None` — via `solana program set-upgrade-authority --final` — which makes the program permanently immutable \[[Solana docs — Program Deployment](https://solana.com/docs/core/programs/program-deployment)\] \[[QuickNode — How to Make an Immutable Solana Program](https://www.quicknode.com/guides/solana-development/anchor/how-to-make-immutible-solana-programs)\]. Setting it to the all-zero system-program address is the conventional "burn" — also irreversible \[\[QuickNode, same\]\].

Two facts matter for a fund-custody program specifically:

- **State survives upgrades; the code governing that state does not.** Data accounts (the LP vault's token accounts, ticket PDAs) are untouched by an upgrade. But because the *new* bytecode is what interprets and authorizes movement out of those same PDAs going forward, "the code that owns the vault changed" is functionally equivalent to "whoever controls the upgrade key controls the vault" — the account/code separation is a deployment-mechanics fact, not a safety boundary \[[Solana docs — Core Accounts](https://solana.com/docs/core/accounts)\] \[[ChainScore Labs — Architecting for Solana Program Upgradability](https://chainscorelabs.com/guides/decentralized-applications-dapps-and-platforms/solana-dapp-development/how-to-architect-for-solana-program-upgradability)\].
- **There is no protocol-native timelock.** Any delay has to be built either into who is allowed to sign (a multisig with its own delay feature) or into the calling program's own logic. Solana ships neither a native cooldown on the loader instruction nor a mempool where a pending upgrade could be observed before it lands — it is one signed instruction away from execution the moment the authority signs \[[Solana docs — bpf\_loader\_upgradeable](https://docs.rs/safecoin-program/latest/solana_program/bpf_loader_upgradeable/index.html)\].

Best practice, confirmed across multiple sources, is to make the upgrade authority a PDA/multisig rather than a raw keypair specifically so a delay and an approval quorum can be layered on top of the otherwise-instant loader instruction \[[ChainScore Labs, same](https://chainscorelabs.com/guides/decentralized-applications-dapps-and-platforms/solana-dapp-development/how-to-architect-for-solana-program-upgradability)\] \[[sec3 — Solana Internals Part 2](https://sec3.dev/blog/solana-internals-part-2-how-is-a-solana-program-deployed-and-upgraded)\].

### 1.2 What Squads v4 actually offers today

Squads Protocol v4 is the de facto standard: 85+ Solana programs delegate their upgrade authority to a Squads multisig, including Raydium, MarginFi, Kamino, Jupiter, and Francium \[[Squads — Managing Program Upgrades with Multisig](https://squads.xyz/blog/solana-multisig-program-upgrades-management)\]. MarginFi and Kamino specifically use it to govern lending-market/reserve program authority, the closest existing analog to Fade's LP-vault situation \[[Squads — MarginFi Spotlight](https://squads.xyz/blog/marginfi-lending-protocol-solana)\]. The core protocol has been audited by OtterSec, Neodyme, and Trail of Bits, with Certora formal verification \[[Fystack — Squads From Zero](https://fystack.io/blog/squads-from-zero-to-the-multisig-protocol-securing-10b-on-solana)\].

v4 ships four features directly relevant here:

- **Time-locks.** A multisig can be configured with a delay (in seconds) via a `SetTimelock` config action. The delay is a freeze *after* the approval threshold is reached, not from proposal creation — the countdown starts once enough signers have approved \[[Squads Docs — Time-locks](https://docs.squads.so/main/development/reference/time-locks)\].
- **Cancellation is a separate, same-threshold tally.** Voting to cancel doesn't withdraw your original approval or reset the countdown — it adds to a distinct cancel count that needs the *same* threshold to succeed. A minority that spots a mistake after approving cannot unilaterally stop it; they need to convince as many members to cancel as originally approved \[[Squads-Protocol/v4 GitHub Issue #135](https://github.com/Squads-Protocol/v4/issues/135)\]. This is a real limitation, not a theoretical one — see §1.3.
- **Roles** (Proposer / Voter / Executor) and **spending limits** (pre-approved allowances a single member can move without full quorum) \[[Squads — Spending Limits](https://squads.xyz/blog/spending-limits)\].
- **Sub-accounts** — one multisig, multiple independently-permissioned vaults (e.g. Payroll vs. R&D) \[[Squads v4 docs, general](https://github.com/Squads-Protocol/v4)\].

What Squads does **not** give you, based on available documentation: no evidence of a delay that starts at proposal-creation rather than threshold-reached, and no built-in LP/user notification pipeline — visibility is "the transaction is a public on-chain account," not "someone pushes a notification to you." Anything beyond on-chain readability is Fade's own responsibility (§2).

### 1.3 The precedent that should scare any team using a multisig as upgrade authority

On April 1, 2026, Drift Protocol — a Solana perpetuals DEX with its own insurance fund and LP-style vaults, governed by a 5-member Security Council multisig — lost $285.3M. The attackers spent weeks inducing two of the five signers to pre-sign malicious governance transactions using Solana's **durable nonce** mechanism, which lets a signed transaction remain valid indefinitely instead of expiring after Solana's normal \~90-second recent-blockhash window \[[The Hacker News](https://thehackernews.com/2026/04/drift-loses-285-million-in-durable.html)\] \[[BlockSec — Drift Protocol Incident](https://blocksec.com/blog/drift-protocol-incident-multisig-governance-compromise-via-durable-nonce-exploitation)\]. Those two signatures, held in reserve for over a week, were enough: on the day of the attack the pre-signed transactions listed a wash-traded fake token as valid collateral, raised a withdrawal limit to roughly $500 trillion, and executed 31 withdrawals in about 12 minutes \[[The Hacker News, same](https://thehackernews.com/2026/04/drift-loses-285-million-in-durable.html)\] \[[Chainalysis — Lessons from the Drift Hack](https://www.chainalysis.com/blog/lessons-from-the-drift-hack/)\]. Drift's own insurance fund survived only because the protocol was paused before losses passed through the normal liquidation pathway \[[crypto.news — Drift insurance fund untouched](https://crypto.news/drift-says-insurance-fund-untouched-after-attack-withdrawals-to-resume/)\]. This was not a smart-contract bug; it was an operational-security failure in exactly the layer this section specifies.

**The concrete lesson, translated into Fade's runbook (mandatory, not aspirational):**

1. No Upgrade Council signer may approve, or hold, a durable-nonce transaction targeting Fade's upgrade authority, ever. Before approving, every signer must independently verify there is no active nonce account associated with the proposer's key \[[Medium — Fortifying Squads](https://medium.com/@aboladeevans/fortifying-squads-advanced-strategies-for-secure-multi-sig-signing-on-solana-453b8f4fed3d)\].
2. No blind signing. Every signer simulates the transaction and inspects the decoded instruction/account list on a trusted display before approving — the entire Drift attack worked because signers approved something other than what they thought they were approving \[[Medium — Fortifying Squads, same](https://medium.com/@aboladeevans/fortifying-squads-advanced-strategies-for-secure-multi-sig-signing-on-solana-453b8f4fed3d)\].
3. Detection has to happen *before* approval, not after — Squads' cancellation quorum (§1.2) is symmetric with approval, so a minority realizing a mistake post-approval cannot reliably stop it.
4. Because a compromised or malicious quorum can replace Fade's *entire* program logic — including every safeguard in this document — the only durable mitigations are (a) raising the number/independence of signers who'd all have to be fooled or compromised simultaneously, and (b) the 72h public delay in §2, which cannot prevent a determined attacker but guarantees the attempt is loud and slow rather than silent and instant.

Also on record: Raydium lost \~$2.2M in December 2022 to a single compromised admin *keypair* (no multisig at all) \[[Helius — Solana Hacks History](https://www.helius.dev/blog/solana-hacks)\], and Serum's upgrade key was a private key controlled by FTX rather than the nominal Serum DAO — a single point of failure severe enough that the community abandoned the program and forked to OpenBook under DAO-managed authority once FTX collapsed \[[Squads — Managing Program Upgrades](https://squads.xyz/blog/solana-multisig-program-upgrades-management)\]. Both are the baseline case against which "4-of-7 hardware-wallet Squads multisig" is an improvement, not a solution.

### 1.4 Recommendation

- Upgrade authority = a Squads v4 multisig PDA, **4-of-7**, hardware-wallet signers only (no raw keypairs, no browser extension wallets for this specific role), members drawn from outside a single office/device/employer where possible.
- 72-hour Squads time-lock on any transaction touching the upgrade authority (upgrade itself, or authority reassignment).
- Every upgrade proposal ships with **verified-build metadata already attached** before any signer approves: source, commit hash, and a reproducible build hash produced by the Ellipsis Labs / OtterSec `solana-verify` tool, which builds in a deterministic container and stores the metadata in an on-chain PDA so *anyone* — not just signers — can independently confirm the deployed bytecode matches the published diff. Drift, Phoenix, and Squads itself already use this pipeline \[[GitHub — Ellipsis-Labs/solana-verifiable-build](https://github.com/Ellipsis-Labs/solana-verifiable-build)\] \[[Solana docs — Verified Builds](https://solana.com/docs/programs/verified-builds)\].
- **Not burned in V1.** Rationale and conditions in §7.

## 2. Timelock design and the LP-exit interaction

### 2.1 Delay and notification

- Delay: 72 hours, Squads-enforced, starting when the 4-of-7 threshold is reached (per §1.2, this is when Squads' own countdown begins — proposals are visible on-chain from creation, so the *effective* observation window for a diligent LP is "time to reach threshold" (typically the slower part) plus the fixed 72h).
- Notification is **on-chain-verifiable, not a promise to communicate**: Fade will run (or integrate with) an open-source upgrade-authority watcher in the mold of `solana-upgrade-watch`, `solgov`, or `authority-sentinel` — all three exist specifically to resolve a program's upgrade authority, Squads config, and any queued proposal straight from on-chain accounts and alert on change, with `solgov` explicitly built *because of* the Drift incident \[[GitHub — EdgeVault/solgov](https://github.com/EdgeVault/solgov)\] \[[GitHub — simonvellin/solana-upgrade-watch](https://github.com/simonvellin/solana-upgrade-watch)\] \[[GitHub — nellupop/authority-sentinel](https://github.com/nellupop/authority-sentinel)\]. Fade's own frontend surfaces a "pending upgrade" banner reading directly from the Squads proposal account and the verified-build PDA — LPs are never asked to trust a tweet.

### 2.2 The exit interaction, worked precisely

The stated design rule is: LP withdrawals are blocked only up to currently reserved liability, never beyond. This directly determines what a timelock can and cannot protect:

- **Unreserved capital** (`vault_total − reserved_liability`) is withdrawable at the next epoch strike (600 s), timelock or no timelock, pause or no pause. A queued upgrade changes nothing about this — an LP who wants out of their unreserved share can request it the instant they decide to and is paid at the next strike, during the entire 72h window.
- **Reserved capital** (backing currently-open tickets) is, by construction, never immediately withdrawable — that's what "reserved" means; it's the capital the open ticket's payout math currently depends on. No timelock length fixes this, because it isn't a governance-visibility problem, it's a solvency problem: the capital is doing something right now.
- The lever that actually matters is **whether reserved liability can grow during the delay**. If new tickets keep opening against the same vault while an upgrade is queued, an LP's capital could stay reserved indefinitely, and the 72h "protection" becomes theater — LPs watch the clock but can't act on what they see.

**Mandatory rule:** any Squads proposal targeting the upgrade authority (or the oracle-program-id / treasury-address parameters, both graded upgrade-severity in §3) must be preceded — as a separate, immediately-executed action, not bundled into the same timelocked proposal — by the Pause Guardian calling `set_pause_flags` with the tickets flag set. This must happen *before or at* the moment the upgrade proposal is created, and Fade's own frontend/watcher treats "an upgrade-authority proposal exists on-chain with `paused_new_tickets=false`" as a process violation to alert on immediately, independent of whether the team remembered to follow the runbook.

With `paused_new_tickets=true` in force for the whole 72h window: reserved liability can only shrink (as open tickets settle — bounded by VRF fulfillment latency, which is on the order of seconds to low minutes, not days) and can never grow. In practice, the overwhelming majority of an LP's position becomes withdrawable well inside the 72h window purely from ticket turnover, and the *entire* unreserved share is withdrawable from second one. The timelock's real value is not "LPs can always get 100% out before an upgrade" (that's structurally impossible while any ticket is open) — it's "LPs get 72 hours of public notice during which their exposure to the pending change is actively shrinking rather than static or growing." That is the honest, precise answer to whether LPs can exit during the delay.

## 3. Parameter governance and classification

**Governing rule, stated once so it doesn't need repeating per row:** `settle_ticket` must be a pure function of the ticket account's own fields plus the VRF output. It must never read live global config. This is what makes permissionless settlement safe to leave permissionless forever — there is nothing left for a parameter change landing between `open_ticket` and `settle_ticket` to bite into, because settlement doesn't consult the parameter at all. Every parameter that participates in the `open_ticket` acceptance decision or the reservation-sizing math is therefore either (a) snapshotted into the ticket account at open time, or (b) graded upgrade-severity if changing it would change the *shape* of that math rather than a threshold inside it (a shape change is a code change and must go through §1's 72h upgrade path, never a lightweight parameter instruction — this boundary exists specifically to stop a shape change from being smuggled through the cheap path to dodge the long timelock).

| Parameter | Can it harm an in-flight ticket? | Can it harm an existing LP position? | Snapshot at `open_ticket`? | Timelock | Notes |
| --- | --- | --- | --- | --- | --- |
| `min_vault_margin_bps` (the vault margin floor) | No — not read at settlement | No, not retroactively | **Yes** (the ticket stores `margin_bps` and `vault_margin_bps`) | Raise: instant. Lower: 7 days | Raising the floor only makes future acceptance stricter; lowering it worsens LP economics going forward, so it gets the asymmetric delay. |
| `protocol_share_bps` (share split) | No | Yes, going forward | **Yes** | Raising it, which cuts the LP's share: 7 days. Lowering it: instant | This is the parameter closest to an LP's expected yield; a cut needs the longest non-upgrade delay in the table. |
| Per-ticket cap's censorship term (150 bps of `total_assets` — one of the two inputs to the computed minimum `min(0.5 · vault_margin/10_000 · free_balance, 150 bps · total_assets)`, §2 of the Technical Specification) and `kelly_fraction_bps` | **No if snapshotted** — reservation is locked at open time regardless of later changes | No | **Yes** — the *computed* cap value is snapshotted at open, not just this one input | Tighten: instant. Loosen: 24h | Lowering it after a ticket opens must never retroactively shrink that ticket's already-reserved payout; snapshotting the computed cap makes this a non-issue for correctness, the delay exists only so integrators aren't blindsided in their UI. |
| Full payout table (`p_i`, `m_i` for every outcome) | No — not read at settlement | No, not retroactively | **Yes** — the entire payout table is snapshotted at open, alongside `margin_bps` | N/A — the payout table is an argument of each `open_ticket`, not a parameter | Settlement must be a pure function of the ticket's own snapshotted fields (the governing rule stated once at the top of this section); the payout table is exactly such a field. |
| The integrator ceiling (20 % of assets), the 70 % utilisation and 15 %/24 h drawdown thresholds | No | Somewhat (raises the vault's tail risk going forward) | Not needed (gates acceptance, not settlement) | Lower: instant. Raise: 24h | Same asymmetry as `margin_bps` — tightening can never strand anything already open; loosening increases risk LPs didn't sign up for. |
| `min_price` (7.5 USDC once SIMD-0437 is fully active, derived from the SOL overhead, Technical Specification §3.7) | No (snapshotted with the ticket) | No | Not needed | Raise: instant. Lower: 24h | Follows the SOL price and Solana's rent, recomputed manually at a ±30 % move of SOL flagged by an off-chain watcher and at each rent step; raising it protects the fair-price claim, lowering it loosens. No price oracle in V1. |
| `epoch_length_seconds` (600) | No — epochs never gate settlement | Yes, going forward (a shorter epoch narrows the anti-sandwich margin, Spec 01 §3.3) | N/A | Lengthen: instant. Shorten: 24h, and only with a measured p99 latency behind it (Technical Specification §3.8) | Never indexed to TVL or volume. A change applies to the next close computed, when the next epoch opens: an epoch that already has a close keeps it, and requests already queued clear under the epoch they were queued in (Spec 08 §4). |
| `T_SETTLE` (150 slots) | Yes if shortened below an in-flight ticket's remaining window — so a ticket keeps the `T_SETTLE` it was opened under | No | **Yes** (`expiry_slot` fixed at open) | Lengthen: instant. Shorten: 24h, with a measured p99 (Technical Specification §8 item 2) | Slot-denominated, so slot-time changes never force a retune. The program accepts 10 to 400 slots: at least a few slots of request window after the earliest request, at most well inside the 512 slots SlotHashes keeps. |

Lower: instant | Too low and keepers stop claiming, so liquidity providers claim for themselves; too high taxes small deposits. Same class as `CRANK_FEE`. |

| Progressive credit (`credit_enabled`, `credit_base`, `credit_rate_bps`), specified and not enabled in V1 | No | No | N/A (read at admission only; an open ticket is never re-checked) | Enable, or lower either constant: instant. | `M_CEILING` (10 000×), `MAX_OUTCOMES` (32), the fixed-point scales | N/A | N/A | Yes (payout table snapshot) | Not a parameter — a code change, 72h upgrade path | Fixed for V1 (Spec 04 §8); exposing them as settable fields would let a cheap instruction change the invariant's shape. |
| VRF/oracle program ID | **No** (in-flight requests already executed against whichever program they were opened against — safe by construction of CPI, no extra snapshotting needed) | Indirectly (a malicious oracle breaks fairness for all future tickets) | N/A | **Same as an upgrade: 72h, Upgrade Council, verified-metadata** | This is the one "parameter" that is actually upgrade-severity: swapping the randomness trust root is equivalent in blast radius to swapping the program logic. |
| Treasury / fee-recipient address | No | No (affects protocol's own revenue, not LP principal) | N/A | 72h, same council as upgrades | Bounded harm (steals future protocol revenue, not LP funds), but treated with upgrade-grade scrutiny because redirection is otherwise a clean, deniable theft-from-the-team vector. |
| Pause flags (new\_tickets / new\_deposits / new\_integrator\_registration / per-integrator) | N/A — this *is* the safety mechanism | N/A | N/A | **None to engage; higher threshold to disengage** | Instant-on is the point; see §4. |
| Fixed-point constants (probability scale, bps scale) and any change to the invariant's *shape* | N/A | N/A | N/A | Not a parameter at all — code change | Must go through the 72h upgrade path. Never expose these as an admin-settable field. |
| Multisig membership of any council | N/A | N/A | N/A | Governed by Squads' own config-change flow, not a Fade instruction | Deliberately kept out of Fade's program entirely — changing who the signers *are* is Squads' problem, not Fade's. |

**How the program enforces the delays.** `Config` holds at most one pending change, `{ params, protocol_treasury, effective_at }` ([Spec 08](08-program-architecture.md) §7). `set_params` applies a change at once when every field it changes tightens; otherwise the change waits, with `effective_at` set by the longest delay among the fields it loosens, a field marked *any change* counting as loosening in both directions. A new `set_params` replaces the pending change and restarts its clock. Once `effective_at` has passed, anyone can apply it with `apply_params`, and the council can withdraw it with `cancel_params` until it is applied. The pending change is public state, so the window a delay promises is one that liquidity providers and integrators can watch on-chain.

## 4. Pause semantics

Fade's config account carries **independent** flags rather than one global switch, because the three failure modes have different blast radii and different legitimate responses:

- `paused_new_tickets: bool`
- `paused_new_deposits: bool`
- `paused_new_integrator_registration: bool`
- `paused_integrators` — a fourth, *targeted* control (see §5c) so one bad integrator doesn't require punishing every honest one on a permissionless, multi-integrator platform. It is a flag in each integrator's own record rather than a set in the config, so that pausing one integrator costs one account write and the config never grows.

In the program the three global flags are bits of `Config.pause_flags` (`PAUSE_TICKETS`, `PAUSE_DEPOSITS`, `PAUSE_NEW_INTEGRATORS`) and the targeted one is `Integrator.paused`; `set_pause_flags(pause_flags, integrator_paused)` writes the bits and, optionally, one integrator's flag (Spec 08 §2.5). The names used below are descriptive.

**What each flag gates, and — critically — what it never touches:**

| Instruction | Gated by |
| --- | --- |
| `open_ticket` | `paused_new_tickets` (global) and `paused_integrators` (per-integrator) |
| `request_deposit` (LP) | `paused_new_deposits` |
| `open_ticket` by an authority with no integrator record yet (its first ticket) | `paused_new_integrator_registration` |
| `request_randomness`, `settle_ticket`, `expire_ticket`, `claim_payout` | **Nothing.** Always callable, permissionless, by design; an open ticket must always be able to close. |
| `request_withdraw` (LP) | **Nothing.** Only the free-liquidity rationing at the strike applies, unconditionally (Spec 01 §4.3). |
| `strike_epoch`, `claim_deposit`, `claim_withdraw` | **Nothing.** A queued request must always be priced and claimable; the strike's only gate is the clean-strike rule (Spec 01 §3.5). |
| `set_share_account` | **Nothing** beyond the integrator authority's signature. |

**Why no pause may ever touch `settle_ticket`, `expire_ticket`, `strike_epoch`, a claim or `request_withdraw`:** the design brief states this as a rule and it is worth defending, not just restating. Blocking settlement of an already-open ticket turns an emergency stop into confiscation of escrowed player funds — the ticket price is the player's money sitting in an account waiting for a promised, deterministic payout function to run; freezing that function is indistinguishable from theft. Blocking LP withdrawal beyond the reserved amount is the identical failure on the other side of the vault: it converts "pause" into a lever the team could use to trap capital, which is precisely the failure mode Solend fell into in June 2022, when a governance vote granted the team "emergency powers" to seize and OTC-liquidate a whale's account to avoid on-chain liquidation chaos — the community's reaction (calling it "the opposite of what DeFi should be," "illegal") was severe enough that Solend reversed the vote within about 48 hours \[[CoinDesk — Solend Emergency Powers Reversal](https://www.coindesk.com/business/2022/06/20/defi-protocol-solend-passes-governance-vote-to-reverse-emergency-powers)\] \[[Cointelegraph — Solend invalidates takeover plan](https://cointelegraph.com/news/solend-invalidates-solana-whale-wallet-takeover-plan-with-second-governance-vote)\]. Fade's rule is designed so that mistake is structurally unavailable, not just discouraged: there is no instruction path from any pause flag to either an escrowed ticket price or LP principal.

**Asymmetry of who can flip which way, modeled on Aave's Guardian design:** Aave separates a fast `EMERGENCY_ADMIN`/Guardian role (can pause/freeze markets) from full governance, and a live 2026 governance proposal specifically restricts the emergency tool to *freezing only* — it cannot unfreeze on its own \[[Bitcoinist — Aave Emergency Freeze Powers](https://bitcoinist.com/aave-governance-weighs-emergency-freeze-powers-for-active-exploits/)\] \[[Aave docs — Governance](https://aave.com/docs/ecosystem/governance)\]. Fade adopts the same asymmetry: the 2-of-3 Pause Guardian may set any flag to `true` (more restrictive) instantly, with no threshold friction, no timelock — that speed is the entire point of the role. Only the 4-of-7 council may set a flag back to `false`. This means a compromised Pause Guardian key can, at worst, produce a temporary, fully recoverable denial of service (no new tickets/deposits/integrators until the council acts) — it cannot move a single lamport, cannot touch an open ticket, cannot touch LP principal.

## 5. Emergency playbook

For each scenario: what the team does, what on-chain capability that requires, and whether the design already has it without adding a rug vector.

**(a) The payout table invariant check is found to be wrong (e.g. an overflow or rounding bug lets `sum(p_i·m_i) > 1 − margin` slip through `open_ticket`).**
Capability used: `paused_new_tickets` (global or, if isolated to one integrator's payout table shape, `paused_integrators`) — already exists, zero new capability. Already-open tickets opened under the bad math still settle exactly as promised via the untouchable `settle_ticket` path; the vault absorbs whatever is already committed, bounded by the exposure-cap parameter (§3) that limits how much any single bug can have reserved before detection. The fix ships only through the normal 72h verified-build upgrade (§1) — a math bug is explicitly *not* grounds for a faster, less-verified path, because a rushed emergency upgrade is exactly the kind of shortcut that turns "one bug" into "one bug plus a backdoor."

**(b) The VRF oracle stops fulfilling requests.**
This must resolve without any admin judgment call — an admin capability to "decide" a stuck ticket's outcome is precisely the kind of discretionary lever that critics correctly call a rug vector (see Hyperliquid, §6/§8). Two oracle implementations were checked for how they actually fail: ORAO's oracle enforces a configurable slot-based deadline for its callback — Solana can't catch a CPI error, so once the deadline passes the request is still marked fulfilled on-chain but the callback into the caller's program is simply skipped, i.e. a caller that doesn't plan for this is left with a request that will never resolve \[[GitHub — orao-network/solana-vrf](https://github.com/orao-network/solana-vrf/blob/master/callback/README.md)\]. Switchboard has moved away from the two-phase request/fulfill model (v2 VRF) toward a v3 "Randomness Service" that generates the value and invokes the callback atomically in the same transaction, removing the stuck-pending state entirely \[[Switchboard docs — Randomness](https://docs.switchboard.xyz/docs-by-chain/solana-svm/randomness)\]. **Interface requirement this section imposes on the ticket/VRF flow (owned by another section of this spec, stated here because it is a governance boundary):** `open_ticket` records `open_slot`; after `T_SETTLE`, a permissionless `expire_ticket` instruction — callable by anyone, exactly like `settle_ticket` — forfeits the ticket price to the vault and releases the reservation deterministically. It does not return the price: returning it would make withholding the randomness a free option for a colluding player-and-oracle pair, so forfeiture costs the player exactly what an honest loss would have (§3.2 of the Technical Specification). No admin instruction may exist that settles a ticket's *outcome* on a timeout; the only admin action in this scenario is the pre-existing `paused_new_tickets` (or a targeted per-oracle pause) while the team investigates. Switching to a different oracle program permanently goes through the oracle-program-id parameter, which §3 already grades as upgrade-severity (72h, verified metadata) precisely because it changes the fairness trust root.

**(c) An integrator is draining the vault.**
Capability used: `paused_integrators` — a targeted pause added specifically because "permissionless to integrate" plus "the only way to stop a bad actor is to stop everyone" is an unacceptable trade-off for a multi-integrator platform. It stops new tickets from that integrator only; already-open tickets from the same integrator still settle normally (the non-negotiable rule holds even for a malicious counterparty), so the damage is capped by whatever that integrator's exposure limit already bounded it to. No rug vector: the flag can't move funds, can't alter payouts, can't touch other integrators.

**(d) Vault accounting is found to be off.**
Capabilities used: `paused_new_deposits` (protects new LPs from buying into a mispriced share) and `paused_new_tickets` (stops the error compounding) — both pre-existing, no new capability. Existing LPs keep withdrawing against the unreserved balance throughout, per the absolute rule in §4. If the *unreserved figure itself* can't be trusted, that is a code bug requiring a §1 upgrade, not a governance fix — **there must never be an admin instruction that directly overwrites an LP's share balance or the vault's aggregate ledger.** An instruction that "corrects one number by fiat" is indistinguishable from an instruction that lets an admin steal, no matter how well-intentioned the immediate motive; a code upgrade that fixes the *formula* for all future computation is the only acceptable remedy, and it goes through the same 72h path as everything else in §1.

## 6. Rug-vector self-audit

Adversarial read of every admin capability this document introduces or preserves:

**Pause Guardian (2-of-3, instant-set-to-restrictive).** Malicious use: griefing — halt onboarding/new-tickets/new-deposits, DoS the protocol until the 4-of-7 council reverses it. Bound: structurally cannot touch a lamport of player or LP principal, cannot change payout math, cannot touch an open ticket. Worst case is a fully recoverable denial of service. This is the entire reason its capability set is restricted to boolean flags and nothing else.

**Parameter authority (4-of-7, same council as upgrades in V1).** Malicious use: zero the margin floor, cut the vault margin, redirect the treasury address, or — the one lever with real teeth — swap the oracle program ID to something that always resolves in the vault's favor. Bound: everything snapshotted at `open_ticket` (margin floor, share split, payout cap) can only bias *future* tickets, and future exposure is itself capped by the exposure-limit parameter. The two levers that could do real damage — oracle-ID swap and treasury redirect — are deliberately graded upgrade-severity (72h, verified metadata, same council process as §1.3's durable-nonce/no-blind-signing discipline) specifically because they are, functionally, upgrades. With that grading in place, a malicious parameter authority cannot touch a single lamport of already-deposited principal or an already-open ticket's promised payout — only future economics, on the same public delay as a code upgrade.

**Upgrade Council (4-of-7, the BPF upgrade authority).** Malicious use: replace 100% of the program's logic, including every rule in this document, and drain the vault PDA directly — categorically unbounded, because the upgrade instruction lives at the SPL loader level, entirely outside Fade's own program, so no Fade-level safeguard constrains what a new deployment can do to accounts Fade's old code owned. This is the risk the design brief names as dominant, and no amount of parameter cleverness changes that fact. What bounds it: (a) 4-of-7 hardware-key quorum, no single point of failure; (b) 72h public delay that cannot be skipped, during which (c) the mandatory pre-emptive `paused_new_tickets` step (§2.2) actively shrinks the LP capital actually at risk; (d) mandatory verified-build metadata published *before* signing, so the diff is checkable by anyone, not just signers, from the moment a proposal exists; (e) the Drift-derived, mandatory no-durable-nonce / no-blind-signing signing discipline (§1.3), which is a process control because Squads' own cancellation mechanism (same threshold as approval) cannot reliably undo a mistake after the fact. Honest statement of the residual risk: this converts "instant, silent theft" into "theft with 72 hours of loud, public, verifiable advance notice, during which exposure is actively decreasing" — it does not, and cannot, eliminate the risk. Only §7's decentralization path improves this further, by shrinking and diversifying who holds the key, not by any code change on Fade's side.

**The line that must never be crossed, regardless of how a future incident makes it tempting:** no admin instruction may ever (1) directly rewrite an LP's balance or share count, (2) directly set or override a ticket's settlement outcome or payout, or (3) move funds out of the vault PDA outside the normal user paths — `request_deposit`, `request_withdraw`, `strike_epoch`, `claim_deposit`, `claim_withdraw`, `settle_ticket`, `expire_ticket` and `claim_payout`. Each of these, if it existed, would be a cleaner, cheaper theft vector than the upgrade authority itself — no 72h delay, no verified diff, no public visibility — so none of them may ever be added, no matter how a specific incident (Solend's whale, a vault-accounting bug, an integrator draining the vault) makes a targeted "just this once" fix look appealing.

## 7. Decentralization path

Dated and milestone-gated, not aspirational:

- **Phase 0 — devnet through early mainnet.** Exactly the configuration in §0: 4-of-7 team-held Upgrade Council, 72h timelock, verified builds mandatory, boolean+targeted pause flags, per-ticket snapshotting, and the hard "never" list in §6. Published publicly as this document — the honest V1 disclosure the team wants on record.
- **Phase 1 — gated on \~90 days of incident-free mainnet operation *and* a completed third-party audit of the invariant check and vault accounting.** Add at least one independent, named, non-team signer to the Upgrade Council (a respected external security researcher or a partner protocol's ops lead), moving toward something like 5-of-9, specifically to raise the number of people who would all have to be fooled or compromised at once (the direct lesson of §1.3). Publish signer roster and org/geographic diversity on the same on-chain watcher dashboard used for §2.1 notifications.
- **Phase 2 — gated on a concrete TVL and volume threshold (to be finalized against the team's own risk tolerance, but should be stated as a number, not "eventually") demonstrating the invariant holds under real, sustained volume.** Migrate the *parameter* authority — not the upgrade authority — to an SPL-Governance (Realms) token- or reputation-weighted realm, preserving the same per-parameter on-chain timelocks from §3 (governance changes *who decides*, not the safety rails already compiled into the program). The Upgrade Council stays a small multisig; a DAO is a bad first responder for time-critical security operations, which is exactly why GMX keeps its Timelock's operational buffer (5–7 days on critical changes) contract-enforced rather than vote-enforced for anything urgent \[[GMX Timelock.sol](https://github.com/gmx-io/gmx-contracts/blob/master/contracts/peripherals/Timelock.sol)\].
- **Phase 3 — gated on Phase 2 governance operating for a defined period (e.g. 6+ months) with a demonstrated track record of actually exercising its votes, not phase-2-in-name-only.** Consider folding the Pause Guardian's fast path into the broader council. Recommendation against ever fully removing a fast, narrow circuit breaker: Hyperliquid's own trajectory after the March 2025 JELLY incident (§8) was not "remove validators' ability to act fast," it was "make the fast action itself fully on-chain and rule-bound instead of ad hoc" \[[thecurrencyanalytics — Hyperliquid On-Chain Validation](https://thecurrencyanalytics.com/altcoins/hyperliquid-implements-on-chain-validation-after-jelly-incident-167612)\]. Fade's end state should keep a fast, bounded, publicly auditable pause path permanently, with an ever-larger and more independent set of keyholders, rather than promise zero fast-response capability.
- **On burning the upgrade authority: explicitly not on the near-term roadmap, and here is why rather than a hand-wave.** The industry-standard guidance is that burning is appropriate for *finalized, extensively audited, long-track-record* contracts \[[QuickNode — Immutable Solana Programs](https://www.quicknode.com/guides/solana-development/anchor/how-to-make-immutible-solana-programs)\] — an early-stage program is definitionally none of those things. Burning prematurely would strand LP funds behind any future undiscovered bug *permanently*, which is a strictly worse outcome for LPs than a well-guarded, timelocked multisig key; it would also trade a recoverable risk (compromise, bounded by §6) for an unrecoverable one (any bug at all, unbounded). Even the most credible long-running Solana-adjacent trust-minimized system studied here, Wormhole's guardian network, has not moved to literal immutability after years of operation — it runs a large (19), reputation-diverse, 13-of-19 threshold set instead \[[Wormhole docs — Guardians](https://wormhole.com/docs/protocol/infrastructure/guardians/)\]. That — large, diverse, high-threshold, permanently held — is the realistic decentralization end-state Fade should be judged against, not a burn date.
